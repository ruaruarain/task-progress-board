# 设计说明：为什么长这样

这份文档解释几个"看起来可以简化、但我们刻意没那么做"的决定。想改结构之前先读一遍，能省掉一次返工。

## 1 为什么是「一份数据源 + 两个产物」

**备选方案**：维护一个 Markdown 看板，HTML 从 Markdown 渲染；或者只做一个网页，让 AI 直接读网页。

**为什么不行**：
- Markdown 无法表达"权重 / 阶段 / 卡点"这些结构，AI 读起来要靠猜
- 只做网页的话，AI 需要能渲染或抓取 HTML，链路变脆；而 AI 真正需要的是**结构化的待办队列**，不是排版
- 两份人工维护的数据源 100% 会漂移（写过文档的人都知道）

**所以**：`看板数据.json` 是唯一事实来源，`生成看板.py` 一次生成两个面向不同读者的视图，`_自检.py` 校验两者数字一致（改了数据忘重新生成会直接失败）。同源 + 双视图 + 一致性校验，是这套东西能长期不烂的原因。

## 2 为什么完成度要加权

**备选方案**：完成度 = 已完成子项数 / 总子项数。

**为什么会误导**：假设 30 个子项里 20 个做完了，等权算是 67%。但如果没做完的 10 个里有 2 个是"坏了整个模块就废"的环节（比如数据源接错、编译不过），真实可用度可能不到 20%。

**所以**：`Σ(权重 × 完成度) / Σ权重`，权重 1~5，5 = 决定该模块能否交付。
实测效果：本项目 L1 链 30 个子项里 21 个是 100%，但因为"功率取值错误"（权重 5）只有 10%，加权后整体 48%——这才是"不能用"的真实反映。

**代价**：权重是主观判断，需要有人负责。`board-maintain` 技能里给了判定尺度和判断问句，避免"为了好看调权重"。

## 3 为什么流程图按「阶段」分列，而不是画真实依赖箭头

**备选方案**：给 129 个子项两两维护有向边，用 DAG 布局算法画真正的依赖图。

**为什么没做**：
- 维护成本极高：加一个子项就要想"它依赖谁"
- 视觉上会糊：100+ 节点的 DAG 在单屏里必然交叉成毛线团
- **我们真正要表达的信息只有两类**：哪些能并行、哪些有先后

**所以**：只维护"阶段"这一个字段。同阶段 = 可并行（画在同一列），阶段 = 先后（列间箭头）。
代价是丢失了"跨阶段的个别依赖"（例如某个后阶段的子项其实不依赖前一阶段）。这个精度损失换来的是**可维护**——加子项时只要填一个阶段名。

## 4 为什么体检要"拦住"而不是"提示"

**备选方案**：所有规则只警告，不阻断生成。

**为什么不行**：看板的价值完全建立在"数字可信"上。一旦允许带病生成：
- "100% 但还挂着卡点"会让读者以为完成了
- "未完成但没写还差什么"会让 AI 接手时无从下手
- "路径写成绝对盘符"会让整个文件夹搬到别的电脑后全部链接失效

**所以**：这三类直接判**错误**并拒绝生成；措辞、格式类只给**警告**。
分界线是"会不会让读者/AI 判断错"。

## 5 为什么同步也要做成有标准的（两个技能）

**问题**：看板最大的敌人不是写不出来，而是**慢慢过期**。一旦"实际做了但没记录"，看板就开始撒谎。

**所以**：把"怎么记"固化成 `progress-sync`（四阶段 + 字段规范 + 完成度判定 + 反例），把"怎么改结构"固化成 `board-maintain`。
两条技能都明确写死：**永不自动执行，只在用户要求时执行**——因为同步会改写产物和进度数据，节奏必须由人决定。

## 6 为什么是单文件 HTML

- 断网可用、不需要服务器、不需要装前端框架 → 双击就能看
- 数据内嵌在 HTML 里（`<script id="board-data" type="application/json">`）→ 一个文件发出去就能看，不会出现"图裂了"
- 代价：没有多用户协作、没有权限控制。需要这些的话，应该用 Jira/Linear，而不是这个

## 7 已知的取舍清单

| 取舍 | 换来什么 | 代价 |
|---|---|---|
| 权重靠人判断 | 完成度不失真 | 需要有人对权重负责 |
| 阶段制代替真实 DAG | 加子项只需填一个字段 | 丢失跨阶段的个别依赖 |
| 体检阻断生成 | 数字可信 | 急着看板时会被拦 |
| 单文件 HTML | 零依赖、可离线 | 无协作、无权限 |
| 示例数据虚构 | 可公开发布 | 使用者要自己替换一遍 |
